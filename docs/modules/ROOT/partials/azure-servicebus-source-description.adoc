== Azure Servicebus Source Kamelet Description

=== Authentication methods

In this Kamelet, you can use these Azure authentication methods:

- Azure Identity mechanism:  `AZURE_IDENTITY`
- Connection string: `CONNECTION_STRING`
- Token credentials: `TOKEN_CREDENTIAL`

The order of evaluation for `AZURE_IDENTITY` is the following:

 - Enviroment
 - Workload Identity 
 - Managed Identity 
 - Azure Developer CLI 
 - IntelliJ
 - Azure CLI
 - Azure Powershell

For more information, see the https://learn.microsoft.com/en-us/java/api/overview/azure/identity-readme[Azure Identity documentation]

For `TOKEN_CREDENTIAL` type, you'll need to add `com.azure.core.credential.TokenCredential` instance in the Camel registry.

`AZURE_IDENTITY` and `TOKEN_CREDENTIAL` also need **fullyQualifiedNamespace**, the host name of the Service Bus namespace, such as `my-namespace.servicebus.windows.net`. Leave **connectionString** unset with them.

=== Topic vs Queue

The subscribtion name parameter needs to be populated in case of consuming from a Topic, while it's not required in case of Queue.

=== Example with Sessions

A queue or subscription created with sessions enabled can be read only with **sessionEnabled** set to `true`. Without
it, the integration receives nothing and logs a warning every few seconds: `It is not possible for an entity that
requires sessions to create a non-sessionful message receiver`. A queue without sessions cannot be read with it.

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:azure-servicebus-source"
      parameters:
        topicOrQueueName: "orders"
        connectionString: "{{servicebus.connection-string}}"
        sessionEnabled: true
        maxConcurrentSessions: 8
      steps:
        - log: "Order $\{body} of session $\{header.CamelAzureServiceBusSessionId}"
----

The messages of one session are received in the order they were sent, and the next one only once the previous one
has been processed (unless a step of the integration works asynchronously, such as a delay). A message whose
processing fails is received again before the next one of its session. Different sessions are read at the same time,
up to **maxConcurrentSessions**, 1 by default, and have no order between them. A session is kept until it has had no
message for a minute: with the default of 1, the messages of another session wait meanwhile.

=== Example Reading the Dead-Letter Queue

Service Bus moves a message to the dead-letter queue of its queue or subscription, for example once its processing
has failed the maximum delivery count of times. Set **subQueue** to `DEAD_LETTER_QUEUE` to read them:

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:azure-servicebus-source"
      parameters:
        topicOrQueueName: "orders"
        connectionString: "{{servicebus.connection-string}}"
        subQueue: "DEAD_LETTER_QUEUE"
      steps:
        - log: "Dead letter $\{body}: $\{header.CamelAzureServiceBusDeadLetterReason} - $\{header.CamelAzureServiceBusDeadLetterErrorDescription}"
----

The dead-letter queue has no sessions, so leave **sessionEnabled** unset, even for a queue with sessions. A
dead-lettered message whose processing fails stays where it is: it is received again straight away, over and over,
and holds up the dead letters behind it. `TRANSFER_DEAD_LETTER_QUEUE` reads the messages that could not be forwarded
or transferred instead.

=== Example Processing Messages in Parallel

The messages are processed one at a time, in the order they arrive, unless a step of the integration works
asynchronously, such as a delay. Set **maxConcurrentCalls** to process that many
at the same time, for example when each message calls a slow service:

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:azure-servicebus-source"
      parameters:
        topicOrQueueName: "orders"
        connectionString: "{{servicebus.connection-string}}"
        maxConcurrentCalls: 5
      steps:
        - to: "http://order-service/orders"
----

With 5, ten messages that take a second each are processed in about two seconds instead of ten, and in no particular
order. With **sessionEnabled**, **maxConcurrentCalls** counts for each session: above 1, the messages of one session
are processed at the same time too, and lose their order.

=== Example Dead-Lettering Failed Messages

By default, a message whose processing fails is given back and received again, until Service Bus moves it to the
dead-letter queue after the maximum delivery count of the queue (10 by default). Set **enableDeadLettering** to `true`
to move it there straight away:

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:azure-servicebus-source"
      parameters:
        topicOrQueueName: "orders"
        connectionString: "{{servicebus.connection-string}}"
        enableDeadLettering: true
      steps:
        - to: "http://order-service/orders"
----

The dead-lettered message has the exception as its reason, such as `java.lang.IllegalStateException: Invalid order`,
and its stack trace as the error description; read them back with **subQueue** set to `DEAD_LETTER_QUEUE`, in the
`CamelAzureServiceBusDeadLetterReason` and `CamelAzureServiceBusDeadLetterErrorDescription` headers. It works only with
the default **serviceBusReceiveMode**, `PEEK_LOCK`, and does nothing while reading the dead-letter queue itself.
