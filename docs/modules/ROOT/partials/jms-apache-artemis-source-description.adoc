== JMS Apache Artemis Source Kamelet Description

=== Authentication

A broker that needs a login takes it in the `username` and `password` options. Without them, the Kamelet connects with
no login.

=== Configuration

The JMS Apache Artemis Source Kamelet supports the following configurations:

- **Broker URL**: Apache Artemis broker URL (required)
- **Destination Name**: JMS destination (queue or topic) name (required)
- **Destination Type**: Type of destination - queue or topic (default: queue)
- **Username** and **Password**: the login to the broker, when it needs one
- **Durable Subscription**, **Shared Subscription**, **Subscription Name** and **Client ID**: a durable or shared
  subscription to a topic (see below)
- **Message Selector**: receive only the messages that match a condition on their properties and headers
- **Transacted**, **Acknowledgement Mode** and **Concurrent Consumers**: delivering a message again when its flow
  fails, and processing several messages at the same time (see below)

=== Output Format

The Kamelet outputs JMS messages including message body, headers, and JMS properties. The body is text for a text
message, bytes for a bytes message, and a Map for a map message.

=== Usage Example

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:jms-apache-artemis-source"
      parameters:
        brokerURL: "tcp://artemis.example.com:61616"
        destinationName: "orders.queue"
        destinationType: "queue"
      steps:
        - to:
            uri: "kamelet:log-sink"
----

=== Example with Topic Subscription

By default, the source receives only the messages published to the topic while it is connected.

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:jms-apache-artemis-source"
      parameters:
        brokerURL: "tcp://artemis.example.com:61616"
        username: "artemisuser"
        password: "artemispass"
        destinationName: "events.topic"
        destinationType: "topic"
      steps:
        - to:
            uri: "kamelet:log-sink"
----

=== Example with a Durable Topic Subscription

With `subscriptionDurable` set to `true`, the broker keeps the messages published to the topic while the source is
stopped, and delivers them when it starts again. The broker keeps the subscription under the client ID and the
subscription name, so use the same `clientId` and `subscriptionName` each time the source starts.

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:jms-apache-artemis-source"
      parameters:
        brokerURL: "tcp://artemis.example.com:61616"
        username: "artemisuser"
        password: "artemispass"
        destinationName: "events.topic"
        destinationType: "topic"
        subscriptionDurable: true
        subscriptionName: "audit"
        clientId: "audit-service"
      steps:
        - to:
            uri: "kamelet:log-sink"
----

The JMS rules to know:

- A durable subscription that is not shared needs a `clientId`. Without one, the source starts but receives nothing,
  and logs that the client ID is not set.
- Only one connection may use a client ID at a time. A second copy of the source with the same `clientId` receives
  nothing, and logs that the client ID is already in use.
- To run several copies of the source on one durable subscription, set `subscriptionShared` to `true` as well, and
  leave `clientId` empty: the copies share the messages of the topic by `subscriptionName`, each message going to one
  of them. Shared subscriptions are part of JMS 2.0.
- The durable subscription stays on the broker, and keeps collecting messages, until it is removed in the broker.

=== Example with a Message Selector

The source receives only the messages that match `selector`, a condition on the JMS properties and headers of the
message. From a queue, the other messages stay on the queue.

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:jms-apache-artemis-source"
      parameters:
        brokerURL: "tcp://artemis.example.com:61616"
        destinationName: "orders.queue"
        selector: "priority > 5"
      steps:
        - to:
            uri: "kamelet:log-sink"
----

=== Redelivery when the flow fails

By default, the source removes each message from the queue when it receives it, so a message whose flow fails is lost.
With `transacted` set to `true`, each message is received in a transaction that is committed only once the flow has
processed it. When the flow fails, the transaction is rolled back and the broker delivers the message again, with the
header `JMSRedelivered` set to `true`.

After 10 attempts, the default of the broker (`max-delivery-attempts`), Artemis moves the message to the dead letter
queue, `DLQ` by default.

`concurrentConsumers` processes several messages of the queue at the same time, each in a thread of its own; the
messages are then no longer processed in the order of the queue.

[source,yaml,subs='+attributes,macros']
----
- route:
    from:
      uri: "kamelet:jms-apache-artemis-source"
      parameters:
        brokerURL: "tcp://artemis.example.com:61616"
        destinationName: "orders.queue"
        transacted: true
        concurrentConsumers: 5
      steps:
        - to:
            uri: "kamelet:log-sink"
----

`acknowledgementModeName` set to `CLIENT_ACKNOWLEDGE` also delivers a message again when its flow fails, without a
transaction. `DUPS_OK_ACKNOWLEDGE` acknowledges the messages in batches: it is faster, but the messages processed since
the last batch are delivered again after a crash.

=== Connection Management

When the broker cannot be reached, the Kamelet starts anyway and tries to connect again every 5 seconds. It does not
pool connections, and does not need to: it keeps its connection open while it receives.
